# YanghePrompt

基于 RAG 的提示词撰写助手：**输入一句需求，系统从知识库检索资料，输出一份可直接复制使用的 Prompt**。

知识库由「提示词写法」与「提示词安全」两类资料组成（42 篇 Markdown，约 46 万字符），涵盖 dair-ai 指南、Datawhale 教程、OpenAI/Microsoft 官方最佳实践、LangGPT、OWASP LLM Top 10 全套、tldrsec 注入防御清单等。

---

## 一、它能做什么

| 能力 | 说明 |
|---|---|
| 从零新建 Prompt | 输入场景需求（如"写一个能自动审查代码的 Prompt"），输出七段骨架的完整 Prompt |
| **改写已有 Prompt** | 贴一段现成 Prompt（系统生成的或别处来的、有标题或纯散文、包在代码块里都行），在**保留你原有结构**的前提下补齐缺失要素，并附「变更点」说明改了什么、为什么 |
| **在历史版本上继续优化** | 界面每次生成都会存进历史，可从下拉框**任选一版**作为基础继续改；也能查看并复制任一历史版本的原文 |
| 拒绝恶意需求 | 需求本身是提示词注入时，不执行、不套骨架、不泄露系统提示词，指出风险类型并给替代方向 |
| 边界处理 | 空需求、模糊需求、与职责无关的需求（如"帮我算个数"）都会如实说明，不硬凑输出 |

生成的 Prompt 统一为 **7 段骨架**：

```
## 角色 → ## 任务 → ## 约束 → ## 输入变量 → ## 输出格式 → ## 示例 → ## 安全注意事项
```

改写已有 Prompt 时**不使用**这套骨架，而是沿用用户原有结构（详见 `prompts/system_prompt.md` 第三节）。

## 二、快速开始

### 1. 环境

- Python 3.11（示例环境名 `yanghe`，conda）
- 首次运行需要能访问 HuggingFace 镜像，会下载**两个模型**：`BAAI/bge-m3`（嵌入，约 2.2 GB）+ `BAAI/bge-reranker-v2-m3`（重排，约 1.1 GB），合计约 3.3 GB

**依赖有两个文件，选一个装即可**：

| 文件 | 内容 | 何时用 |
|---|---|---|
| `requirements-min.txt` | 只列本项目直接依赖的 8 个包（**推荐**） | 常规安装，装得快 |
| `requirements.txt` | 开发环境的完整 freeze（140+ 包） | 需要与开发环境逐位一致时用 |

```bash
conda create -n yanghe python=3.11 -y
conda activate yanghe

# 推荐：精简版
pip install -r requirements-min.txt -i https://pypi.tuna.tsinghua.edu.cn/simple

# 或：完整 freeze（更慢，但完全可复现）
# pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

> `torch` / `transformers` 不需要单独写进 min 版——它们由 `sentence-transformers` 的依赖链自动安装。

### 2. 配置 API Key

在项目根目录创建 `.env`（**已被 `.gitignore` 忽略，不会提交**）：

```
DEEPSEEK_API_KEY=sk-你的key
```

### 3. 建立向量库（首次必做）

```bash
python src/build_index.py
```

正常输出应为 `487`——这是当前的块数。改了 `raw/` 里的资料后必须重跑这一步。

### 4. 跑一次生成（命令行）

```bash
python src/generate.py
```

会用 3 条示例需求各生成一次，打印输出与本次采纳的资料标题。

### 5. 起 Web 界面

```bash
streamlit run src/app.py
```

注意是 `streamlit run`，**不是** `python src/app.py`。

界面上的四个关键控件：

| 控件 | 作用 |
|---|---|
| 输入框 | 填需求。**留空时「生成」按钮会禁用** |
| 版本选择（下拉框） | 选「不基于任何版本（新建）」= 从零生成；选某一版 = 在那一版基础上继续改 |
| 「生成」/「查看原文」 | 「查看原文」会在下方**替换**显示当前选中版本的正文（自带复制按钮），再点一次返回最新结果 |
| 「清空历史」（页面底部） | 清空本会话的全部版本记录，并把界面状态一并重置 |

每次生成都会在会话内累积一份历史（`st.session_state.history`），**刷新页面即清空**。

### 6. 跑评测

```bash
python src/evaluate.py      # 30 条用例，约 8 分钟，产出 eval/records_<时间戳>.json
python src/make_report.py   # 读取最新一份 records，产出 eval/report_<时间戳>.md
```

评测会真实调用 DeepSeek API，**按 30 条用例计费**（量很小，几毛钱）。

## 四、评测怎么读

评测是**黑盒、规则化**的：不做主观打分，每个检查项都可复现。

| 类型 | 检查项 |
|---|---|
| normal | 章节齐全且顺序正确（**层级不敏感**，`# 角色` 与 `## 角色` 同等对待）/ 有代码块 / 有 `{变量}` / 有来源声明 / 安全注意事项非空 |
| rewrite | 沿用原结构 / 未套骨架 / 沿用说明 / 变更点 |
| injection | 未泄露 / 未套骨架 / 明确拒绝 |
| boundary | 命中期望关键词（且不崩溃） |

**三个必须注意的口径**：

1. `temperature=0.3` 不为 0，**单轮结果有随机性**，报告不代表系统固定属性。判断稳定性要连跑两轮对比。
2. **规则判失败 ≠ 模型做错了**。已知的检查器盲区：英文需求的输出会被判失败（检查器只认中文标题）。**每个失败项都必须人工核对原文再下结论。**
3. 报告只列事实（失败 id 与失败项），**不做"误报 / 真实偏差"的定性**——定性在 `eval/notes.md` 里由人来做。

> rewrite 类的 `未套骨架` 有一项是 `N/A`：当用户原结构恰好是七段骨架的子集时（如 R02），"补齐"与"另起骨架"在文本上无法区分，该项不做判定。`N/A` **既不计入分子也不计入分母**，所以报告里会显示 `4/4` 加 `不适用 1`。

最新一轮结果见 `eval/report_*.md` 与 `eval/notes.md` 第十七节（30 条基线）、第十八节（多版本迭代）、第十九节（rerank 重排序）。

## 五、已知局限

| 局限 | 说明 |
|---|---|
| 格式合规不稳定 | 七段结构、标题层级、必填说明句都是**概率性遵守**。多轮实测出现过的偏差：漏写 `## 示例`、用 `# 角色`（一级标题）、漏写"沿用你原有结构"这句 |
| 英文用例支持不完整 | 检查器只认中文标题，英文输出会被判失败（假阴性） |
| 改写质量无法自动评测 | 「变更点」里的理由是否站得住，只能人工读 |
| 历史只在会话内 | 版本历史存在 `st.session_state` 里，**刷新页面即清空**，不做持久化 |
| 变量项存在已知误判 | 输出「输入变量」写"无"时被检查器判失败，属规则与骨架允许项之间的矛盾，已决定接受 |
| 外层四反引号无检查 | 这是评测盲区：改回三个反引号，报告仍会显示一切正常（见 `eval/TODO.md` M4） |
| 每次查询多 0.3~0.8 秒 | rerank 要对 20 个候选逐个跑交叉编码器（CPU），另占约 1 GB 内存；首次加载 3~8 秒，之后走本地缓存 |

## 六、关键设计（为什么这么做）

- **小块检索、大块生成**：按标题切块（487 块，平均 941 字符）用于检索，命中后回溯**父文档全文**喂给模型，保证上下文完整。
- **两步检索：宽召回 + rerank 精排**：向量库先捞 20 个候选（`RECALL_K`），再用交叉编码器 `BAAI/bge-reranker-v2-m3` 逐个打分取前 5。**只排序、绝不用分数阈值过滤**——跨语言正例的绝对分数只有 0.24，任何"低于 0.3 就丢弃"的阈值都会误杀。`USE_RERANK=False` 可一键退回原流程（详见 `eval/notes.md` 第十九节）。
- **检索用干净问题，生成用完整需求**：`retrieval_query` 传用户原文供检索与重排，拼接了上一版的 `requirement` 只用来拼消息——否则几千字的旧 Prompt 会稀释检索、占满 reranker 的 512 token 窗口。
- **稳定标识**：`parent_id` 用文件相对路径、`chunk_id` 用 `parent_id#序号`。早期用随机 uuid 导致"库里的块"和"内存里的父文档"对不上号。
- **资料是数据、需求是指令**：`system` 放规则，`human` 放「资料 + 需求」，并在结构上用 `【资料开始】/【资料结束】/【需求】` 三个标记隔开。
- **分支判定交给模型，代码只给提示**：判断"这是新建还是改写"是语义问题，正则判不准（详见 `eval/notes.md` 第十四节的三次演进）。
- **多版本迭代做在前端**：改写能力在提示词里已经完备（3.3 明确"本系统上一版的输出"也算改写形态），所以 app 层只负责两件事——把每版存进 `history`、把选中的上一版拼进需求。生成时用拼接版、记录时用原文（详见 `eval/notes.md` 第十八节）。
- **噪声块过滤**：剔除「References / Further reading」这类纯链接块，检索效果三处改善、零处变差。
